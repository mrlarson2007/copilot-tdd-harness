# Eval Report Site (Prototypes)

Static pages that present the harness eval results to visitors. There is no
build step: open `site/index.html` in a browser, or serve the `site/` folder
with any static host (for example GitHub Pages).

> **The current data is sample data.** `data/eval-report.js` was generated to
> exercise the layouts. The numbers are not real measurements. Every page shows a
> banner while `isSample` is `true`.

The **Jev Live Evaluation** Actions run Summary uses its own Markdown scorecard,
generated by `evals/promptfoo/jev-report.js` exclusively from recorded Jev
results. It borrows the overview-and-expandable-details layout, not this site's
sample data, comparison metrics, or builder. See the
[Jev workflow documentation](../evals/promptfoo/README.md#safe-manual-github-actions-setup).
GitHub Actions does not render these interactive HTML prototypes in the Summary.

## Prototypes

| Prototype | Path | Idea |
| --- | --- | --- |
| A · Scorecard | `prototype-a-scorecard/` | One leaderboard: overall score per model with the harness and with no skills, plus the lift. Expand a row for per-metric detail. |
| B · Dashboard | `prototype-b-dashboard/` | Filter by scenario and metric. Shows a grouped bar chart, a model × metric heatmap, and a per-scenario table. |
| C · Story | `prototype-c-story/` | A before/after page covering test-first rate, a typical run timeline, failure modes, lift per model, and cost. |

All three use the same data file (`data/eval-report.js`) and the same helpers
(`assets/report.js`, `assets/base.css`).

## Data contract

`data/eval-report.js` sets `window.EVAL_REPORT`. The data is loaded with a
script tag instead of `fetch`, so the pages also work when opened from
`file://`.

| Field | Meaning |
| --- | --- |
| `isSample`, `sampleNotice` | Shows the sample-data banner while `isSample` is true. |
| `conditions` | `harness` (`copilot --agent=tdd` with the `tdd-*` skills) and `baseline` (the default agent with no skills). Both get the same prompt and fixture. |
| `models` | `{ id, label, tier }` for each model evaluated. |
| `metrics` | `{ id, label, description, source }`. Each metric maps to an assertion in `evals/promptfoo/assertions/` or to a run-summary field. |
| `scenarios` | `{ id, label, fixtureId, family }`, matching the promptfoo test cases. |
| `failureModes` | `{ id, label }` for each failure mode shown in the story page. |
| `runs[]` | One entry per (model, condition, scenario) cell: `trials`, `passes` (passed-trial count per metric, listing only the metrics that apply), `failureModes` (count per id), `medianDurationSec`, `medianCommits`. |

Pass rates are pooled as passes ÷ trials. The "overall score" is the
unweighted mean of the per-metric pass rates.

## Putting real results on the dashboard

You need the Copilot CLI (`copilot`) installed and signed in, plus Go and .NET
for the fixtures.

1. **Generate results.** Run the eval matrix for each model, with and without
   the harness. Use `--repeat` to get more than one trial per cell:

   ```bash
   ./scripts/run-evals.sh --condition both --model claude-sonnet-4.5,gpt-5 --repeat 3
   ./scripts/run-evals.sh --extended --condition both --model claude-sonnet-4.5,gpt-5
   ```

   ```powershell
   .\scripts\run-evals.ps1 -Condition both -Model claude-sonnet-4.5,gpt-5 -Repeat 3
   ```

   Each model × condition run writes one promptfoo result file to
   `evals/promptfoo/results/runs/`. That folder is git-ignored. Results build
   up across runs, so you can add a model later without re-running the others.
   Delete files from that folder to drop old results.

2. **Build the report data.**

   ```bash
   node scripts/build-eval-report.js
   ```

   This reads every file in `evals/promptfoo/results/runs/` and overwrites
   `site/data/eval-report.js` with `isSample: false`, which also removes the
   sample banner. Open `site/index.html` to check the result.

3. **Publish.** Commit `site/data/eval-report.js`. If GitHub Pages serves
   `site/`, visitors see the new numbers after the commit lands.

The builder only counts the TDD fixture scenarios. It skips the
`commit-discipline-failure` self-test (it checks the eval tooling, not the
agent) and the requirements-planning scenario. Rows where the provider crashed
without producing a run summary are skipped and reported in the console output.

### How the two conditions differ

| | `harness` | `baseline` |
| --- | --- | --- |
| Files copied into the fixture workspace | `tdd` agent, `tdd-*` skills, contracts | none |
| Copilot invocation | `copilot --agent=tdd [--model M] --prompt ...` | `copilot [--model M] --prompt ...` |
| Prompt, fixture, scoring | same | same |

The scripts set the `EVAL_CONDITION` and `EVAL_MODEL` environment variables,
which `evals/fixtures/scenarios/agent-runner.js` reads. You can also set them
yourself when calling promptfoo directly.
